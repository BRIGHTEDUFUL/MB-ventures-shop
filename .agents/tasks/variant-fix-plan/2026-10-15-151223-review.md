# Variant picker chips now reflect user selection

The change fixes an always-frozen `selectedOptions` computation in `product.$slug.tsx` that prevented colour and size chips from responding to user taps. The root cause was a guard condition (`axes.every(axis => axis.values.includes(""))`) that could never be true, so `selectedOptions` was always the first variant's options regardless of what `setChosen` was called with. Three targeted edits — seeding `chosen` from the first visible variant, merging user choices over defaults, and using a functional `setChosen` update — resolve this. The fix is entirely front-end; the backend (orders, stock, catalogue) was already correct.

Watch for: the `useEffect` dependency array suppresses the `variants` warning with `// eslint-disable-next-line react-hooks/exhaustive-deps` — this is acceptable here but means the effect won't re-fire if variants change without a slug change (confirmed: not a concern in practice because variants are tied to the product which is tied to the slug).

**Verdict**: APPROVED

## High-level view

The hook ordering is now correct: `axes`, `variants`, `chosen`, `quantity`, and the seeding `useEffect` all appear before the `if (!p) return <PageNotFound />` guard, satisfying React's rules-of-hooks constraint. This was identified in the plan as an existing violation in the pre-fix code.

The `useEffect` seeds `chosen` with `firstVisible?.options ?? {}` on slug change, meaning the picker is never in a blank state. Combined with the merge `{ ...defaultOptions, ...chosen }`, user clicks accumulate correctly: the first render shows the default variant pre-selected, and each subsequent click updates exactly the axis that was tapped without disturbing the others.

The `onSelect` callback was changed from `setChosen({ ...selectedOptions, [axis]: value })` to `setChosen((prev) => ({ ...prev, [axis]: value }))`. The functional update form is strictly correct and avoids a subtle stale-closure issue where spreading `selectedOptions` (a derived value) rather than `prev` (the raw state) could re-introduce defaults on each click.

The `VariantPicker` component itself has no bugs — the `cells.get(variantKey({ ...selected, [axis.name]: value }, axisNames))` lookup and the `disabled`/`aria-pressed` logic are correct given an accurate `selected` prop.

### Hook ordering before the early return

All `useState` calls (`quantity`, `zone`, `gallery`, `zoom`, `chosen`) and the `useEffect` that seeds `chosen` on slug change appear before the `if (!p) return <PageNotFound />` guard. The `axes` and `variants` constants, which the `useEffect` closure reads, are declared with `p?.axes ?? []` and `p?.variants ?? []` above the guard so they are always defined values (never accessed on a null `p`). This satisfies React's rules-of-hooks requirement. **Confirmed** by reading lines 44–78 of the file.

### Chosen seeded from first visible variant

```ts
useEffect(() => {
  const firstVisible = variants.find((v) => v.visible);
  setChosen(firstVisible?.options ?? {});
  setQuantity(1);
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [slug]);
```

Fires once per slug (not per render). When a product has no variants `firstVisible` is `undefined`, so `chosen` is set to `{}` — which is the same as the old behaviour for no-variant products. **Confirmed** at lines 60–66.

### selectedOptions merges chosen over defaults

```ts
const defaultOptions = variants.find((v) => v.visible)?.options ?? variants[0]?.options ?? {};
const selectedOptions = axes.length > 0 ? { ...defaultOptions, ...chosen } : defaultOptions;
```

For a no-variant product (`axes.length === 0`) this returns `defaultOptions = {}`. For a variant product, `chosen` entries win over the defaults, so clicking "White" produces `{ Colour: "White", Size: <default> }` rather than requiring the user to select every axis before anything registers. **Confirmed** at lines 82–83.

### Functional update in onSelect

```ts
onSelect={(axis, value) => setChosen((prev) => ({ ...prev, [axis]: value }))}
```

Merges onto the raw state rather than onto the derived `selectedOptions`. This is the correct form — it avoids the stale closure issue and keeps user choices accumulating independently of the defaults. **Confirmed** at line 138.
